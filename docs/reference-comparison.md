## 为什么不照搬 Redisson 锁

分布式锁不是唯一正确答案。当前订单链路已经用以下约束构成最终一致性防线：

1. Redis Lua 原子预留，快速拒绝无库存和重复用户。
2. `order_requests(user_id, voucher_id)` 唯一约束，防止重复请求落库。
3. `voucher_orders(request_id)` 与 `(user_id, voucher_id)` 唯一约束，防止重复消费生成两张订单。
4. 数据库条件扣减和事务，保证实际库存不会小于零。
5. Kafka 消费者可以重复收到消息，处理结果仍保持幂等。

Redisson 仍值得单独学习看门狗、可重入和锁续期，但不应替代数据库唯一约束。可以在后续实验中把它作为减少热点冲突的性能层，再故意停掉 Redis，观察数据库防线是否仍能保护结果。

## 下一步建议

1. 先完成 [多实例秒杀压测](multi-instance-load-guide.md)，用数据证明现有边界。
2. 再实现 Redis 分布式业务编号，区分“公开订单号”和数据库主键。
3. 最后做后端镜像、反向代理和可观测性，避免在业务还没有验收前先扩大部署复杂度。
